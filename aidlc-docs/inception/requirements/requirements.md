# OTT 통합 피드 및 AI 추천 서비스 요구사항

## 1. 의도 분석

- **최초 요청**: OTT 최신 정보 피드와 추천 서비스를 구축한다.
- **요청 유형**: 신규 Greenfield 제품
- **출시 형태**: 반응형 웹 애플리케이션
- **대상 사용자**: 한국 및 글로벌 사용자
- **초기 범위**: 글로벌 주요 OTT 중심의 개인 프로젝트·프로토타입
- **범위 추정**: 피드, 검색, 추천, 계정, 데이터 수집, 관리 기능을 포함하는 시스템 전체
- **복잡도 추정**: 중간 이상. 외부 데이터 의존성, 생성형 AI, 개인화, 개인정보, 복원력 요구가 결합됨
- **요구사항 깊이**: Standard 상세도

## 2. 제품 비전

사용자가 여러 OTT 서비스를 개별적으로 탐색하지 않아도 최신 콘텐츠를 한 화면에서 확인하고, 자신의 현재 상황을 자연어로 표현하여 적합한 콘텐츠와 이해하기 쉬운 추천 이유를 얻는 서비스를 제공한다.

가장 중요한 성공 기준은 개인화 추천의 클릭률과 사용자 만족도이다. 추천 결과는 일회성 목록이 아니라 사용자의 대화형 조정과 행동 피드백을 반영해 지속적으로 개선되어야 한다.

## 3. 핵심 제품 가치

### 3.1 OTT 최신 콘텐츠 통합 피드

- 글로벌 주요 OTT의 신작, 공개 예정작, 인기 콘텐츠, 서비스 종료 예정 콘텐츠를 통합한다.
- 콘텐츠 제공처, 갱신 시각, 이용 가능 지역을 사용자가 확인할 수 있어야 한다.
- 데이터 공급자가 허용하는 범위에서 준실시간으로 갱신한다.

### 3.2 자연어 기반 AI 추천

- 사용자는 상황과 선호를 문장으로 입력할 수 있어야 한다.
- 예: `퇴근 후 가볍게 볼 1시간 이내 코미디`
- 시스템은 입력에서 기분, 장르, 상영 시간, 분위기, 함께 보는 사람, 이용 가능한 OTT 등의 조건과 의도를 추출해야 한다.

### 3.3 개인 맞춤 콘텐츠 추천

- 초기에는 선호 장르와 구독 OTT를 반영한 규칙 기반 개인화로 시작한다.
- 데이터가 축적되면 시청 이력, 평가, 찜, 클릭, 저장, 다시 추천, OTT 이동 행동을 반영한다.
- 콜드 스타트 사용자는 명시적 선호와 인기·신작 정보를 결합해 추천한다.

### 3.4 AI 추천 이유 및 콘텐츠 요약

- 각 추천 항목에는 짧은 콘텐츠 요약과 사용자의 요청에 맞는 추천 이유를 제공한다.
- 설명은 수집된 콘텐츠 메타데이터에 근거해야 하며 확인되지 않은 줄거리나 제공 정보를 사실처럼 생성해서는 안 된다.
- 스포일러를 최소화하고 생성형 AI가 작성한 문구임을 식별할 수 있어야 한다.

### 3.5 대화형 추천 조정

- 사용자는 `조금 더 밝은 작품`, `다른 장르로 추천해 줘`와 같은 후속 요청으로 추천을 조정할 수 있어야 한다.
- 시스템은 현재 추천 세션의 조건과 사용자가 변경한 조건을 구분해 새로운 결과를 제안해야 한다.
- 사용자는 대화 조건을 초기화하고 새 추천을 시작할 수 있어야 한다.

### 3.6 추천 피드 개인화

- 클릭, 저장, 평가, 다시 추천, 추천 무시, OTT 이동 등의 반응을 수집한다.
- 반응 데이터는 이후 추천 점수와 피드 순서 개선에 사용한다.
- 사용자는 개인화 데이터 사용에 동의하거나 거부할 수 있고, 자신의 데이터를 조회·내보내기·삭제할 수 있어야 한다.

## 4. 사용자 및 외부 Actor

| 역할 | 주요 목적 |
|---|---|
| 방문자 | 통합 피드, 작품 상세, 기본 검색을 탐색한다. |
| 회원 | 선호, 구독 OTT, 찜, 평가, 시청 이력, 알림 및 개인화 추천을 사용한다. |
| 운영자 | 작품 정보와 노출 여부를 검토하고 수정한다. |
| 외부 데이터 공급자 | 콘텐츠 메타데이터와 OTT 제공 정보를 전달한다. |

AI 모델, Recommendation Engine, Metadata Validation Pipeline은 사용자나 외부 Actor가 아니라 시스템 내부 구성요소이므로 Actor 표에서 분리한다.

### 4.1 내부 시스템 책임 경계

| 내부 구성요소 | 책임 | 책임에서 제외되는 사항 |
|---|---|---|
| Recommendation Orchestrator | 추천 요청의 단계 실행, 구성요소 호출 순서, 제한 시간, 실패 처리, 검증 결과와 응답 조립을 관리한다. | 추천 점수 계산이나 자유 형식 콘텐츠 생성을 직접 수행하지 않는다. |
| AI 계층 | 자연어 요청을 구조화된 의도와 조건으로 변환하고, 검증된 메타데이터만 사용해 요약·추천 이유·대화형 조건 변경안을 생성한다. | 후보의 최종 적격성 판단, 하드 필터 우회, 최종 순위 확정, 존재하지 않는 콘텐츠 생성은 수행하지 않는다. |
| Recommendation Engine | 검증된 카탈로그에서 후보를 조회하고 하드 조건 필터링, 점수 계산, 개인화, 다양성 제어, 최종 순위를 결정한다. | 근거 없는 줄거리·사실 생성이나 사용자 문장의 자유 형식 해석을 담당하지 않는다. |
| Metadata Validation Pipeline | 수집 메타데이터와 추천 결과의 스키마, 출처, 최신성, 지역·OTT 가용성, 근거 일치 여부를 검사하고 승인·격리·차단 상태를 결정한다. | 추천 순위를 임의로 변경하거나 검증되지 않은 데이터를 보완 생성하지 않는다. |
| Feedback Processor | 동의된 클릭·저장·평가·다시 추천·OTT 이동 이벤트를 정규화하여 개인화 특성으로 제공한다. | 동의 범위를 벗어난 이벤트 결합이나 직접 식별정보의 AI 전달을 수행하지 않는다. |

## 5. 기능 요구사항

### 5.1 피드 및 콘텐츠

- **FR-001**: 시스템은 여러 글로벌 OTT의 콘텐츠를 하나의 통합 피드로 제공해야 한다.
- **FR-002**: 피드는 신작, 공개 예정, 인기, 서비스 종료 예정 상태를 구분해야 한다.
- **FR-003**: 사용자는 장르, 연도, OTT, 국가, 공개 상태로 피드를 필터링하고 정렬할 수 있어야 한다.
- **FR-004**: 작품 상세에는 제목, 원제, 포스터, 줄거리, 장르, 상영 시간, 출연진, 공개 연도, 연령 정보, 제공 OTT, 이용 가능 지역, 데이터 갱신 시각을 표시해야 한다.
- **FR-005**: 사용자는 지원되는 OTT의 합법적인 작품 시청 또는 상세 페이지로 이동할 수 있어야 한다.
- **FR-006**: 외부 제공 정보가 오래되었거나 제공되지 않을 때 마지막 갱신 시각과 데이터 상태를 표시해야 한다.

### 5.2 검색 및 자연어 탐색

- **FR-007**: 사용자는 제목과 인물로 검색할 수 있어야 한다.
- **FR-008**: 시스템은 자연어 또는 의미 기반 검색을 지원해야 한다.
- **FR-009**: 자연어 요청에서 장르, 분위기, 시청 가능 시간, 동반 시청자, 선호·제외 조건, OTT 조건을 구조화해야 한다.
- **FR-010**: 명확하지 않거나 충돌하는 조건은 사용자에게 이해 가능한 형태로 표시하고 조정할 수 있게 해야 한다.

### 5.3 추천

- **FR-011**: 초기 추천은 사용자의 선호 장르, 구독 OTT, 현재 요청 조건과 콘텐츠 최신성·인기도를 결합해야 한다.
- **FR-012**: 행동 데이터가 축적되면 클릭, 찜, 평가, 시청 이력, 다시 추천, OTT 이동 신호를 개인화 점수에 반영해야 한다.
- **FR-013**: 추천 후보는 이용 가능 OTT, 지역, 상영 시간 등의 명시적 제약을 우선 충족해야 한다.
- **FR-014**: 각 추천에는 사용자 요청과 연결된 짧은 추천 이유를 제공해야 한다.
- **FR-015**: 각 추천에는 스포일러를 최소화한 짧은 콘텐츠 요약을 제공해야 한다.
- **FR-016**: 추천 이유와 요약은 저장된 메타데이터를 근거로 생성하고 근거 데이터가 부족하면 이를 명시해야 한다.
- **FR-017**: 시스템은 추천 결과의 다양성을 보장하여 동일 작품이나 지나치게 유사한 작품의 반복을 제한해야 한다.
- **FR-018**: 추천 응답 실패 시 규칙 기반 인기·신작·장르 추천으로 저하 운용해야 한다.

### 5.4 대화형 추천

- **FR-019**: 사용자는 이전 추천에 후속 자연어 조건을 추가하여 결과를 다시 받을 수 있어야 한다.
- **FR-020**: 시스템은 유지되는 조건, 새로 추가된 조건, 제거되거나 변경된 조건을 추천 세션에 반영해야 한다.
- **FR-021**: 사용자는 추천 세션을 초기화하고 새 대화를 시작할 수 있어야 한다.
- **FR-022**: 대화 이력 보존 기간과 개인화 활용 여부는 사용자가 통제할 수 있어야 한다.

### 5.5 계정 및 개인화 데이터

- **FR-023**: 이메일 로그인과 지원 가능한 소셜 로그인을 제공해야 한다.
- **FR-024**: 회원은 선호 장르, 구독 OTT, 찜, 평가, 시청 이력을 관리할 수 있어야 한다.
- **FR-025**: 시스템은 클릭, 저장, 다시 추천, 추천 무시, OTT 이동 이벤트를 목적과 동의 범위에 맞게 기록해야 한다.
- **FR-026**: 회원은 개인화 데이터 수집 동의를 변경하고 데이터를 조회·내보내기·삭제할 수 있어야 한다.
- **FR-027**: 비회원 행동은 명시적 동의 없이 식별 가능한 회원 프로필에 결합해서는 안 된다.

### 5.6 알림

- **FR-028**: 회원은 찜하거나 관심을 표시한 작품의 신규 공개 및 공개 예정 알림을 설정할 수 있어야 한다.
- **FR-029**: 사용자는 알림 유형과 채널을 켜거나 끌 수 있어야 한다.

### 5.7 관리 기능

- **FR-030**: 운영자는 작품 정보와 노출 여부를 조회하고 수정할 수 있어야 한다.
- **FR-031**: 운영자 변경은 변경자, 시각, 변경 전후 값을 감사 기록으로 남겨야 한다.
- **FR-032**: 자동 수집 데이터와 운영자 수정 값이 충돌할 때 적용 우선순위를 명확히 해야 한다.

### 5.8 다국어

- **FR-033**: 사용자 인터페이스는 최소 한국어와 영어를 지원해야 한다.
- **FR-034**: 작품 제목과 설명은 공급되는 번역을 우선 사용하고, 번역이 없을 때 적용되는 대체 규칙을 제공해야 한다.
- **FR-035**: 검색과 자연어 추천은 한국어와 영어 입력을 처리해야 한다.

### 5.9 추천 생성 및 Metadata 검증 Pipeline

- **FR-036**: AI 계층은 자연어 입력을 정해진 스키마의 구조화된 추천 의도와 조건으로 변환해야 하며, Recommendation Engine은 이 구조화 결과만 추천 입력으로 사용해야 한다.
- **FR-037**: Recommendation Engine은 지역, 구독 OTT, 상영 시간, 공개 상태, 연령 등 하드 조건을 먼저 적용한 뒤 개인화 점수와 다양성 정책으로 최종 순위를 결정해야 한다.
- **FR-038**: AI 계층이 생성한 추천 이유와 요약은 추천 후보별 승인된 메타데이터 필드 및 출처 식별자와 연결되어야 한다.
- **FR-039**: Metadata Validation Pipeline은 사용자에게 노출하기 전에 모든 추천 작품 ID가 승인된 카탈로그에 존재하는지, 현재 요청의 지역·OTT·시간 제약을 충족하는지 검증해야 한다.
- **FR-040**: Metadata Validation Pipeline은 생성된 요약과 추천 이유의 핵심 주장에 대응하는 근거 필드가 존재하는지 검사해야 하며, 근거 없는 주장이 발견되면 해당 문구 또는 추천 항목을 차단해야 한다.
- **FR-041**: 검증 실패 시 시스템은 검증되지 않은 결과를 노출하지 않고, 승인된 메타데이터 템플릿이나 규칙 기반 추천으로 대체해야 한다.
- **FR-042**: 추천 요청마다 의도 해석 버전, 후보 집합, 적용 필터, 점수·순위 버전, 사용 메타데이터 버전, 검증 결과, 대체 경로 여부를 추적 가능한 형태로 기록해야 한다. 개인정보와 모델 내부 추론 내용은 기록하지 않는다.

## 6. 데이터 및 통합 요구사항

- **DR-001**: 콘텐츠 메타데이터는 합법적으로 사용할 수 있는 공개 API와 제휴 데이터를 조합한다.
- **DR-002**: 각 데이터 공급자별 이용 약관, 표시 의무, 저장 허용 범위, 갱신 주기, 지역별 제공 범위를 구현 전에 검토하고 기록한다.
- **DR-003**: 공급자 데이터는 내부 표준 콘텐츠 모델로 정규화하고 원본 식별자와 출처를 보존한다.
- **DR-004**: 동일 작품의 공급자별 레코드를 중복 제거하고 병합하되 출처별 차이를 추적할 수 있어야 한다.
- **DR-005**: 수집 작업은 공급자 요청 제한을 준수하고 실패 항목을 재처리할 수 있어야 한다.
- **DR-006**: 콘텐츠별 마지막 수집 시각, 원본 출처, 데이터 품질 상태를 저장한다.
- **DR-007**: 사용자 행동 이벤트는 이벤트 유형, 작품, 시각, 추천 세션, 노출 위치를 포함하되 불필요한 개인정보를 포함하지 않는다.
- **DR-008**: AI 입력에는 추천에 필요한 최소한의 사용자 특성만 전달하고 직접 식별자는 제거한다.
- **DR-009**: 수집된 메타데이터는 원본 영역, 정규화 영역, 승인 영역, 격리 영역으로 상태를 구분해야 한다.
- **DR-010**: 승인 영역으로 이동하기 전에 필수 필드, 데이터 형식, 출처, 라이선스 상태, 최신성, 지역·OTT 가용성, 식별자 일관성을 검증해야 한다.
- **DR-011**: 검증 규칙 버전과 검증 시각을 저장하고 실패 레코드는 원인 코드와 함께 격리하여 사용자 피드와 추천 후보에서 제외해야 한다.
- **DR-012**: Recommendation Engine은 승인 상태의 메타데이터만 후보 생성과 순위 계산에 사용할 수 있어야 한다.
- **DR-013**: AI 요약·추천 이유 입력은 승인된 후보의 허용된 근거 필드로 제한하고 각 입력 필드의 콘텐츠 ID와 출처를 유지해야 한다.
- **DR-014**: 추천 결과 검증 기록은 추천 세션, 콘텐츠 ID, 메타데이터 버전, 검증 규칙 버전, 통과·실패 상태와 실패 코드를 포함해야 한다.

## 7. 비기능 요구사항

### 7.1 성능 및 규모

- 초기 프로토타입은 동시 사용자 10명 미만을 기준으로 한다.
- 캐시된 피드와 작품 상세의 초기 목표는 정상 조건에서 p95 2초 이내이다.
- 일반 검색의 초기 목표는 p95 3초 이내이다.
- AI 추천의 초기 목표는 정상적인 외부 AI 응답 조건에서 p95 10초 이내이며, 처리 중 상태를 사용자에게 표시한다.
- 외부 API 및 AI 서비스 호출에는 명시적 연결·응답 제한 시간을 적용한다.

### 7.2 최신성

- 데이터 공급자가 허용하는 범위에서 준실시간 갱신을 목표로 한다.
- 공급자별 요청 제한으로 목표를 달성할 수 없을 때 실제 갱신 주기와 마지막 성공 시각을 표시한다.
- 수집 실패가 기존 정상 데이터를 즉시 삭제하거나 손상시키면 안 된다.

### 7.3 보안

보안 확장은 비활성화되었지만 다음 핵심 보안 요구사항은 일반 요구사항으로 필수 적용한다.

- 인증 자격 증명은 안전하게 해시 또는 외부 인증 공급자를 통해 관리한다.
- 세션과 토큰은 만료, 폐기, 재발급 정책을 가져야 한다.
- 회원, 운영자 권한을 분리하고 서버 측에서 모든 권한을 검증한다.
- 전송 데이터와 저장된 민감정보를 암호화한다.
- 비밀정보는 소스 코드와 컨테이너 이미지에 포함하지 않고 별도 비밀정보 관리 방식으로 주입한다.
- 입력 검증, 출력 인코딩, 요청 제한, 감사 로그를 적용한다.
- 의존성 및 컨테이너 이미지 취약점 검사를 CI에 포함한다.

### 7.4 개인정보 및 접근성

- 상용 전환 전에 대상 국가별 개인정보 및 소비자 보호 요구사항에 대한 법무 검토를 완료해야 한다.
- 개인정보 처리 목적, 보존 기간, 제3자 AI·데이터 공급자 전송 범위를 고지하고 동의를 관리한다.
- 사용자 데이터 조회, 내보내기, 삭제 및 동의 철회를 지원한다.
- 적용할 접근성 표준 버전은 구현 계획에서 확정하되 AA 수준을 목표로 키보드 사용, 명확한 포커스, 대체 텍스트, 색 대비, 스크린 리더 호환성을 검증한다.

### 7.5 AI 품질 및 책임성

- 추천 결과는 명시적 조건 충족 여부와 추천 이유를 함께 제공한다.
- 추천 이유와 요약은 근거 메타데이터를 벗어난 사실을 단정하지 않아야 한다.
- AI가 생성한 콘텐츠는 Recommendation Engine의 후보 적격성·순위를 변경할 권한이 없으며 Metadata Validation Pipeline을 통과해야만 노출할 수 있다.
- 검증할 수 없는 자유 형식 주장은 제거하고 승인된 메타데이터 기반 템플릿으로 대체한다.
- 유해하거나 부적절한 자연어 입력에 대해 안전한 오류 메시지와 처리 정책을 적용한다.
- 추천 품질은 클릭률뿐 아니라 저장률, OTT 이동률, 다시 추천 비율, 사용자 평가 및 다양성 지표로 평가한다.
- AI 모델 또는 공급자 변경이 추천 품질과 응답 형식을 훼손하지 않도록 회귀 평가 세트를 유지한다.

### 7.6 유지보수 및 이식성

- React 계열 프론트엔드와 Python 백엔드를 사용한다.
- 애플리케이션은 Docker 기반으로 실행하며 특정 클라우드에 종속되지 않는 인터페이스를 우선한다.
- 프로토타입 인프라 구성은 버전 관리되는 Docker Compose 및 배포 설정으로 정의한다.
- 콘텐츠 공급자와 AI 제공자는 어댑터 경계를 통해 교체 가능하게 설계한다.

### 7.7 관측성

- 백엔드는 구조화 로그, 요청 상관관계 ID, 주요 지연 시간, 오류율, 처리량 지표를 제공한다.
- 외부 콘텐츠 API, AI 서비스, 데이터베이스 연결 상태를 확인하는 얕은·깊은 상태 점검을 제공한다.
- 피드 갱신 실패, AI 오류율, 백업 실패, 외부 API 한도, 데이터 최신성 저하에 대한 알림 기준을 정의한다.
- 단일 서버 프로토타입에서는 분산 추적이 필수는 아니며 서비스가 분리될 때 적용한다.

### 7.8 테스트 가능성

- 예제 기반 단위·통합·사용자 흐름 테스트와 속성 기반 테스트를 함께 사용한다.
- 추천 제약 조건, 점수 범위, 중복 제거, 정렬, 필터링, 데이터 정규화, 직렬화 왕복에 대한 불변 속성을 식별한다.
- 추천 결과의 모든 콘텐츠가 승인 카탈로그에 속하고 하드 조건을 충족하며, 요약·추천 이유의 근거 참조가 유효하다는 속성을 검증한다.
- 검증 실패 레코드가 승인 영역이나 사용자 응답으로 유출되지 않는 격리 불변 조건을 검증한다.
- Python 속성 기반 테스트 프레임워크는 NFR Requirements 단계에서 확정하고 축소 및 시드 재현을 지원해야 한다.
- 속성 기반 테스트에서 발견된 최소 실패 사례는 영구 회귀 테스트로 추가한다.

## 8. 복원력 요구사항

### 8.1 작업 부하 중요도

| 작업 부하 | 초기 중요도 | 중단 영향 | 주요 의존성 |
|---|---|---|---|
| 사용자 피드·검색·추천 API | High | 제품의 핵심 가치 사용 불가 | 콘텐츠 저장소, AI 서비스, 캐시 |
| 계정·개인화 데이터 | High | 로그인과 개인화 중단, 개인정보 영향 | 인증 계층, 데이터베이스 |
| 콘텐츠 수집 작업 | Medium | 피드가 오래되지만 기존 데이터로 조회 가능 | 외부 콘텐츠 공급자 |
| 관리 기능 | Low | 운영자 수정 지연, 일반 사용자 기능은 유지 | 계정·콘텐츠 저장소 |

### 8.2 가용성 및 복구

- 프로토타입 가용성 목표는 계획된 유지보수를 제외한 월 99.0%이며 계약상 SLA는 제공하지 않는다.
- RTO와 RPO는 수 시간 범위로 설정하고 백업 및 복원 전략을 사용한다.
- 프로토타입은 단일 리전·단일 서버로 운영하며 Multi-AZ와 다중 리전은 적용하지 않는다.
- Multi-AZ 미적용은 프로토타입 한정 예외이다. 상용 공개 전 위험·비용을 재평가하고 운영 환경에는 다중 가용 영역을 기본 요구로 검토한다.

### 8.3 배포 및 변경 관리

- 개인 프로젝트 프로토타입이므로 공식 조직 변경 관리에서는 제외한다.
- Git 커밋, 릴리스 태그, 배포 기록을 변경 이력으로 유지한다.
- GitHub Actions, Docker, GHCR 기반 CI/CD를 제안하고 구현한다.
- 직접 배포 방식을 사용하며 실패 시 이전 버전의 이미지와 배포 설정을 다시 배포한다.
- 데이터베이스 마이그레이션은 이전 애플리케이션 버전과의 호환성 또는 별도 복구 절차를 가져야 한다.

### 8.4 장애 격리 및 저하 운용

- 모든 외부 호출에는 제한 시간, 제한된 재시도와 지수 백오프를 적용한다.
- 외부 공급자와 AI 서비스 장애가 전체 애플리케이션 장애로 전파되지 않도록 회로 차단 또는 동등한 격리 방식을 적용한다.
- 콘텐츠 공급자 장애 시 마지막 정상 데이터로 피드를 제공한다.
- AI 서비스 장애 시 규칙 기반 추천으로 전환하고 사용자가 현재 제한 상태를 알 수 있게 한다.

### 8.5 백업 및 장애 대응

- 사용자, 개인화, 콘텐츠 운영 데이터에 자동화된 암호화 백업을 적용한다.
- 초기 백업 보존 목표는 30일이며 복원 검증 절차를 문서화한다.
- 장애 탐지, 영향 확인, 임시 완화, 복구, 사용자 공지, 사후 분석을 포함한 경량 장애 대응 절차를 제안한다.
- 상세 복구·복원 실행서와 복원 테스트 일정은 설계 및 Build and Test 단계에서 작성한다.

| 대화 조정 후 전환 개선율 | 후속 요청이 추천 품질을 개선하는지 측정한다. |

| 데이터 최신성 충족률 | 공급자별 목표 갱신 주기를 만족하는지 측정한다. |

- 무단 스크래핑이나 이용 약관을 위반하는 데이터 수집
- 초기 프로토타입의 다중 리전 또는 Multi-AZ 배포
- 초기 단계의 대규모 트래픽용 자동 확장
- 완전 자동화된 편집·큐레이션 운영 콘솔
- 법률 또는 접근성 인증의 자동 보장

## 12. 핵심 인수 기준

- **AC-001**: 사용자는 하나의 반응형 화면에서 여러 글로벌 OTT의 신작·인기·공개 예정·종료 예정 콘텐츠를 확인할 수 있다.
- **AC-002**: 사용자가 자연어로 상황을 입력하면 시스템은 핵심 조건을 표시하고 조건에 맞는 추천 결과를 반환한다.
- **AC-003**: 각 AI 추천은 짧은 요약과 사용자 조건에 연결된 추천 이유를 포함한다.
- **AC-004**: 사용자의 후속 요청은 이전 추천 세션을 유지하면서 지정된 조건만 변경한다.
- **AC-005**: 클릭, 저장, 평가, 다시 추천, OTT 이동 이벤트가 동의 범위 안에서 기록되고 이후 추천에 반영된다.
- **AC-006**: AI 서비스가 실패해도 규칙 기반 추천과 기존 콘텐츠 피드는 계속 사용할 수 있다.
- **AC-007**: 회원은 자신의 개인화 데이터를 내보내고 삭제하며 수집 동의를 철회할 수 있다.
- **AC-008**: 데이터 공급자별 출처와 마지막 갱신 시각을 확인할 수 있다.
- **AC-009**: 추천 및 데이터 변환의 핵심 불변 조건은 예제 기반 테스트와 속성 기반 테스트로 검증된다.
- **AC-010**: Docker 기반 로컬 실행과 GitHub Actions 기반 빌드·테스트·이미지 게시 절차가 재현 가능하다.
- **AC-011**: AI 계층이 반환한 후보가 하드 조건을 위반해도 Recommendation Engine과 Metadata Validation Pipeline이 이를 최종 응답에서 제외한다.
- **AC-012**: 사용자에게 노출되는 모든 추천 콘텐츠 ID는 승인된 카탈로그 레코드와 일치하고 지역·OTT 가용성 검증을 통과한다.
- **AC-013**: 추천 이유와 요약의 핵심 주장마다 승인된 메타데이터 근거가 존재하며, 근거가 없으면 해당 문구가 차단되거나 템플릿으로 대체된다.
- **AC-014**: 스키마·출처·최신성 검증에 실패한 수집 레코드는 격리되고 피드·검색·추천에 노출되지 않는다.
